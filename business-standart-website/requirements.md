# Документ требований: Веб-сайт Business Standart

## Введение

Данный документ содержит формальные требования к веб-платформе оценочной компании ООО «BUSINESS STANDART» (Ташкент, Узбекистан). Система предоставляет автоматизированный расчёт стоимости оценочных услуг, интеграцию с платёжными системами Payme/Click, личный кабинет клиента для отслеживания заявок и административную панель для управления контентом и правилами ценообразования.

Система заменяет устаревший сайт (Joomla 1.5) и обеспечивает полную автоматизацию процесса от расчёта стоимости до получения готового документа оценки.

## Глоссарий

- **Система** — веб-платформа Business Standart, включающая backend (FastAPI), frontend (Flutter Web), базу данных PostgreSQL и интеграции с внешними сервисами
- **Калькулятор** — компонент для расчёта предварительной стоимости услуг на основе параметров пользователя
- **Движок_Ценообразования** — backend компонент, применяющий конфигурируемые правила для расчёта стоимости
- **Заявка** — запрос клиента на оказание оценочной услуги с расчётной стоимостью
- **Правило_Ценообразования** — конфигурируемое правило для расчёта стоимости (linear, tiered, flat_addon)
- **Клиент** — физическое или юридическое лицо, использующее услуги оценочной компании
- **Администратор** — сотрудник компании с правами управления контентом, заявками и настройками
- **Детализация** — разбивка расчётной стоимости на составные элементы (breakdown)
- **Платёжная_Транзакция** — запись о платеже через Payme или Click
- **Webhook** — автоматическое уведомление от платёжной системы о статусе платежа
- **Личный_Кабинет** — персональная область клиента для просмотра и управления заявками
- **Модуль_Курсов_Валют** — сервис обновления и отображения официальных курсов ЦБУ
- **Подписанная_Ссылка** — временный URL для скачивания документа из S3 хранилища
- **Карта_Районов** — интерактивная карта регионов/районов Узбекистана для выбора местоположения объекта

## Требования

### Требование 1: Расчёт стоимости оценочных услуг

**Пользовательская история:** Как клиент, я хочу получить предварительный расчёт стоимости услуги на основе параметров моего объекта, чтобы понимать ожидаемую цену до оформления заявки.

#### Критерии приёмки

1. КОГДА клиент выбирает услугу и вводит все обязательные параметры, ТОГДА Калькулятор ДОЛЖЕН вернуть предварительную стоимость в течение 2 секунд
2. КОГДА Движок_Ценообразования выполняет расчёт, ТОГДА Движок_Ценообразования ДОЛЖЕН применить все активные правила ценообразования для выбранной услуги
3. КОГДА расчёт завершён, ТОГДА Система ДОЛЖНА предоставить детализацию с разбивкой по всем применённым правилам
4. ДЛЯ каждого расчёта, сумма всех элементов детализации ДОЛЖНА быть равна итоговой стоимости
5. КОГДА клиент изменяет параметры, ТОГДА Калькулятор ДОЛЖЕН пересчитать стоимость с сохранением детерминированности (одинаковые параметры дают одинаковый результат)
6. ЕСЛИ клиент отправляет некорректные параметры (отрицательные числа, пустые обязательные поля), ТОГДА Система ДОЛЖНА вернуть детализированное сообщение об ошибке валидации на русском языке
7. Калькулятор ДОЛЖЕН поддерживать три типа правил ценообразования: linear (линейная надбавка), tiered (ступенчатая), flat_addon (фиксированная)
8. КОГДА применяется правило типа tiered, ТОГДА Движок_Ценообразования ДОЛЖЕН выбрать диапазон на основе значения параметра и применить соответствующую ставку

### Требование 2: Управление заявками клиентов

**Пользовательская история:** Как клиент, я хочу создать заявку на основе расчёта и отслеживать её статус в личном кабинете, чтобы контролировать процесс оказания услуги.

#### Критерии приёмки

1. КОГДА клиент подтверждает расчёт, ТОГДА Система ДОЛЖНА создать заявку со статусом "ожидание оплаты" и сохранить все параметры расчёта
2. КОГДА заявка создана, ТОГДА Система ДОЛЖНА сгенерировать уникальный идентификатор заявки и вернуть URL для оплаты
3. Система ДОЛЖНА поддерживать следующие статусы заявки: draft, awaiting_payment, paid, in_progress, ready, delivered, cancelled
4. КОГДА клиент запрашивает список своих заявок, ТОГДА Личный_Кабинет ДОЛЖЕН отобразить все заявки пользователя с возможностью фильтрации по статусу
5. КОГДА происходит изменение статуса заявки, ТОГДА Система ДОЛЖНА создать запись в истории изменений с указанием актора, времени и комментария
6. ЕСЛИ клиент пытается изменить статус заявки на недопустимый, ТОГДА Система ДОЛЖНА отклонить запрос и вернуть ошибку с описанием разрешённых переходов
7. КОГДА заявка переходит в статус paid, ТОГДА Система ДОЛЖНА автоматически вычислить и установить дедлайн выполнения (от 2 до 5 рабочих дней)
8. КОГДА заявка переходит в статус ready, ТОГДА Система ДОЛЖНА отправить уведомление клиенту о готовности документа

### Требование 3: Интеграция платёжных систем

**Пользовательская история:** Как клиент, я хочу оплатить заявку онлайн через Payme или Click, чтобы не тратить время на личный визит в офис компании.

#### Критерии приёмки

1. КОГДА клиент выбирает способ оплаты, ТОГДА Система ДОЛЖНА создать платёжную сессию и перенаправить клиента на страницу оплаты выбранной платёжной системы
2. КОГДА платёжная система отправляет webhook о статусе платежа, ТОГДА Система ДОЛЖНА проверить подпись webhook перед обработкой
3. ЕСЛИ подпись webhook невалидна, ТОГДА Система ДОЛЖНА отклонить запрос с HTTP 401 и записать security incident в лог
4. КОГДА получен webhook со статусом success и валидной подписью, ТОГДА Система ДОЛЖНА обновить статус заявки на paid и статус транзакции на success
5. КОГДА платёж успешно обработан, ТОГДА Система ДОЛЖНА отправить уведомления клиенту и сотрудникам компании
6. КОГДА получен повторный webhook с тем же external_id, ТОГДА Система ДОЛЖНА вернуть существующую транзакцию без создания дубликата (идемпотентность)
7. ЕСЛИ платёж провалился, ТОГДА Система ДОЛЖНА обновить статус транзакции на failed и отправить клиенту уведомление с возможностью повторной оплаты
8. Система ДОЛЖНА логировать все платёжные транзакции с сохранением полного payload от платёжной системы
9. КОГДА создаётся платёжная транзакция, ТОГДА Система ДОЛЖНА проверить, что сумма транзакции совпадает с итоговой стоимостью заявки

### Требование 4: Обновление и отображение курсов валют

**Пользовательская история:** Как посетитель сайта, я хочу видеть актуальные курсы валют из ЦБУ на главной странице, чтобы быть в курсе текущих обменных курсов.

#### Критерии приёмки

1. Модуль_Курсов_Валют ДОЛЖЕН обновлять курсы валют ежедневно в 09:00 по Ташкентскому времени через Celery Beat
2. КОГДА запускается задача обновления курсов, ТОГДА Модуль_Курсов_Валют ДОЛЖЕН запросить данные из API ЦБУ для валют: USD, EUR, RUB, GBP, CNY
3. КОГДА получены данные от API ЦБУ, ТОГДА Модуль_Курсов_Валют ДОЛЖЕН вычислить изменение курса относительно предыдущего дня для каждой валюты
4. КОГДА курсы обновлены в базе данных, ТОГДА Модуль_Курсов_Валют ДОЛЖЕН инвалидировать кеш виджета курсов в Redis
5. ЕСЛИ API ЦБУ недоступен или возвращает ошибку, ТОГДА Система ДОЛЖНА повторить попытку через 1 час (максимум 3 попытки)
6. ЕСЛИ все попытки обновления провалились, ТОГДА Система ДОЛЖНА отправить уведомление администратору
7. КОГДА клиент запрашивает данные виджета курсов, ТОГДА Система ДОЛЖНА вернуть закешированные данные с TTL 1 час
8. КОГДА клиент открывает страницу истории курсов, ТОГДА Система ДОЛЖНА предоставить данные за последние 30 дней для выбранной валюты
9. ДЛЯ каждого обновления курсов, Система ДОЛЖНА сохранять уникальную запись по паре (дата, код_валюты)

### Требование 5: Управление документами оценки

**Пользовательская история:** Как клиент, я хочу скачать готовый документ оценки из личного кабинета, чтобы использовать его для своих целей.

#### Критерии приёмки

1. КОГДА администратор загружает готовый PDF документ, ТОГДА Система ДОЛЖНА сохранить его в S3 хранилище с UUID именем файла
2. КОГДА документ успешно загружен в S3, ТОГДА Система ДОЛЖНА обновить статус заявки на ready и сохранить путь к документу
3. КОГДА клиент запрашивает скачивание документа, ТОГДА Система ДОЛЖНА проверить, что заявка принадлежит этому клиенту
4. ЕСЛИ заявка не принадлежит клиенту, ТОГДА Система ДОЛЖНА вернуть HTTP 403 Forbidden
5. ЕСЛИ статус заявки не является ready или delivered, ТОГДА Система ДОЛЖНА вернуть HTTP 400 с сообщением о текущем статусе на русском языке
6. КОГДА клиент имеет право на скачивание, ТОГДА Система ДОЛЖНА сгенерировать подписанную ссылку с временем действия 1 час
7. КОГДА истекает время действия подписанной ссылки, ТОГДА S3_хранилище ДОЛЖНО отклонить запрос на скачивание
8. ЕСЛИ загрузка документа в S3 провалилась, ТОГДА Система ДОЛЖНА сохранить статус заявки без изменений и уведомить администратора об ошибке

### Требование 6: Интерактивная карта районов

**Пользовательская история:** Как клиент, я хочу выбрать район расположения объекта на интерактивной карте, чтобы быстро указать местоположение без ручного ввода.

#### Критерии приёмки

1. Карта_Районов ДОЛЖНА отображать все регионы Узбекистана в виде интерактивных полигонов
2. КОГДА клиент наводит курсор на регион, ТОГДА Карта_Районов ДОЛЖНА подсветить область и показать название региона на русском языке
3. КОГДА клиент кликает на регион "Ташкент", ТОГДА Карта_Районов ДОЛЖНА отобразить детализированную карту районов Ташкента
4. КОГДА клиент кликает на другой регион (не Ташкент), ТОГДА Система ДОЛЖНА перенаправить клиента в Калькулятор с предзаполненным параметром региона
5. КОГДА клиент выбирает район Ташкента, ТОГДА Система ДОЛЖНА перенаправить в Калькулятор с предзаполненными параметрами региона и района
6. Карта_Районов ДОЛЖНА корректно масштабироваться на мобильных устройствах с сенсорным управлением
7. КОГДА загружается Карта_Районов, ТОГДА Система ДОЛЖНА загрузить GeoJSON данные регионов в течение 3 секунд

### Требование 7: Аутентификация и управление пользователями

**Пользовательская история:** Как клиент, я хочу зарегистрироваться и войти в личный кабинет, чтобы управлять своими заявками.

#### Критерии приёмки

1. КОГДА клиент регистрируется, ТОГДА Система ДОЛЖНА принять номер телефона в формате +998XXXXXXXXX и проверить его уникальность
2. КОГДА клиент создаёт пароль, ТОГДА Система ДОЛЖНА принять пароль длиной минимум 8 символов
3. КОГДА пароль сохраняется, ТОГДА Система ДОЛЖНА хешировать его с использованием bcrypt с cost factor 12
4. Система ДОЛЖНА никогда не хранить пароли в открытом виде
5. КОГДА клиент входит в систему, ТОГДА Система ДОЛЖНА проверить соответствие введённого пароля сохранённому хешу
6. КОГДА аутентификация успешна, ТОГДА Система ДОЛЖНА выдать JWT токен с временем жизни 24 часа
7. КОГДА клиент делает запрос к защищённым endpoints, ТОГДА Система ДОЛЖНА проверить валидность JWT токена
8. ЕСЛИ JWT токен истёк или невалиден, ТОГДА Система ДОЛЖНА вернуть HTTP 401 Unauthorized
9. КОГДА клиент регистрируется, ТОГДА Система ДОЛЖНА требовать заполнения поля "Полное имя"

### Требование 8: Административная панель

**Пользовательская история:** Как администратор, я хочу управлять правилами ценообразования, услугами и заявками, чтобы поддерживать актуальность системы.

#### Критерии приёмки

1. КОГДА администратор входит в админ-панель, ТОГДА Система ДОЛЖНА проверить наличие роли администратора у пользователя
2. ЕСЛИ пользователь не является администратором, ТОГДА Система ДОЛЖНА отклонить доступ с HTTP 403 Forbidden
3. КОГДА администратор создаёт или изменяет правило ценообразования, ТОГДА Система ДОЛЖНА валидировать тип правила (linear, tiered, flat_addon)
4. КОГДА создаётся правило типа tiered, ТОГДА Система ДОЛЖНА требовать массив диапазонов с полями min, max, rate
5. КОГДА администратор деактивирует правило ценообразования, ТОГДА Система ДОЛЖНА исключить его из будущих расчётов без удаления из базы данных
6. КОГДА администратор обновляет информацию об услуге, ТОГДА Система ДОЛЖНА требовать уникальность slug и обязательность name_ru
7. КОГДА администратор просматривает список заявок, ТОГДА Система ДОЛЖНА предоставить фильтрацию по статусу, дате и клиенту
8. КОГДА администратор загружает документ для заявки, ТОГДА Система ДОЛЖНА автоматически обновить статус заявки на ready после успешной загрузки

### Требование 9: Уведомления клиентов и администраторов

**Пользовательская история:** Как клиент, я хочу получать уведомления об изменении статуса моей заявки, чтобы быть в курсе процесса.

#### Критерии приёмки

1. КОГДА заявка переходит в статус paid, ТОГДА Система ДОЛЖНА отправить SMS уведомление клиенту с подтверждением оплаты
2. КОГДА заявка переходит в статус ready, ТОГДА Система ДОЛЖНА отправить SMS и email уведомление клиенту о готовности документа
3. КОГДА платёж провалился, ТОГДА Система ДОЛЖНА отправить клиенту уведомление с ссылкой для повторной попытки оплаты
4. КОГДА создаётся новая оплаченная заявка, ТОГДА Система ДОЛЖНА отправить уведомление назначенным сотрудникам компании
5. ЕСЛИ отправка SMS провалилась, ТОГДА Система ДОЛЖНА логировать ошибку и повторить попытку через 5 минут (максимум 3 попытки)
6. Все уведомления клиентам ДОЛЖНЫ быть на русском языке
7. КОГДА формируется текст уведомления, ТОГДА Система ДОЛЖНА включать номер заявки и краткое описание статуса

### Требование 10: Валидация и обработка ошибок

**Пользовательская история:** Как клиент, я хочу получать понятные сообщения об ошибках на русском языке, чтобы исправить свои ошибки ввода.

#### Критерии приёмки

1. КОГДА клиент отправляет форму с невалидными данными, ТОГДА Система ДОЛЖНА вернуть HTTP 422 с детализированным списком ошибок на русском языке
2. КОГДА происходит ошибка валидации, ТОГДА Система ДОЛЖНА указать конкретное поле и причину ошибки
3. ЕСЛИ клиент запрашивает несуществующий ресурс, ТОГДА Система ДОЛЖНА вернуть HTTP 404 с сообщением "Ресурс не найден"
4. КОГДА происходит внутренняя ошибка сервера, ТОГДА Система ДОЛЖНА вернуть HTTP 500 и логировать полную информацию об ошибке
5. ЕСЛИ клиент превышает rate limit (20 запросов в минуту для калькулятора), ТОГДА Система ДОЛЖНА вернуть HTTP 429 с информацией о времени ожидания
6. КОГДА обрабатывается запрос к базе данных и происходит timeout, ТОГДА Система ДОЛЖНА откатить транзакцию и вернуть ошибку клиенту
7. Система ДОЛЖНА никогда не раскрывать внутренние детали реализации в сообщениях об ошибках
8. КОГДА логируется ошибка, ТОГДА Система ДОЛЖНА включать timestamp, уровень ошибки, трейс и контекст запроса

### Требование 11: Производительность и масштабируемость

**Пользовательская история:** Как клиент, я хочу получать быстрые ответы от системы, чтобы не тратить время на ожидание.

#### Критерии приёмки

1. Калькулятор ДОЛЖЕН возвращать результат расчёта в течение 2 секунд для 95% запросов
2. КОГДА клиент запрашивает список заявок, ТОГДА Система ДОЛЖНА вернуть ответ в течение 1 секунды для пользователей с до 1000 заявок
3. КОГДА выполняется запрос к базе данных для таблицы orders, ТОГДА Система ДОЛЖНА использовать составной индекс (user_id, status, created_at)
4. Система ДОЛЖНА использовать connection pool для PostgreSQL с параметрами: min_size=10, max_size=50

### NFR-8: Кроссбраузерная совместимость

Система ДОЛЖНА поддерживать JavaScript ES6+ с полифилами для старых браузеров.

### NFR-9: Масштабирование

Система ДОЛЖНА поддерживать горизонтальное масштабирование backend сервисов через добавление дополнительных инстансов.

### NFR-10: Безопасность соединений

ВСЕ взаимодействия между клиентом и сервером ДОЛЖНЫ использовать HTTPS с TLS 1.2 или выше.

## Ограничения и допущения

### Ограничения

1. Система работает только на территории Узбекистана с поддержкой платёжных систем Payme и Click
2. Все расчёты производятся исключительно в узбекских сумах (UZS)
3. Интерфейс системы доступен только на русском языке
4. Документы оценки генерируются сотрудниками вне системы и загружаются в формате PDF
5. Интеграция с картой ограничена регионами Узбекистана (нет поддержки других стран)
6. Система не предоставляет онлайн-оплату для юридических лиц (только физические лица)
7. Максимальный размер загружаемого PDF документа — 50 МБ

### Допущения

1. Предполагается, что API ЦБУ останется доступным и бесплатным
2. Предполагается, что у клиентов есть доступ к современным браузерам с поддержкой JavaScript
3. Предполагается, что платёжные системы Payme и Click сохранят обратную совместимость API
4. Предполагается наличие стабильного интернет-соединения у клиентов для работы с системой
5. Предполагается, что правила ценообразования не будут меняться чаще одного раза в месяц
6. Предполагается, что среднее время обработки заявки сотрудниками составляет 2-5 рабочих дней
7. Предполагается, что пиковая нагрузка не превысит 500 одновременных пользователей в первый год эксплуатации
